# Dot.Press: Dependency-Patch Approval Pipeline

## Context

Dot.Press' autonomy classification audit (`Dot.Brain/platforms/dot-press.md`, 2026-08-08) found zero queued jobs, scheduled commands, or notifications anywhere in the codebase, and no proposal/approval data model of any kind — the platform's gap summary explicitly names a dependency-patch approval flow as the concrete candidate for its first real Level 2 process, drawn from a real recurring task: `composer audit`/`npm audit` findings, which the platform doc's own "Verified Infrastructure State" history records being triaged and patched by hand during ad hoc passes (23 `composer audit` advisories, 12 `npm audit` issues, most recently 2026-08-07).

Direct inspection confirms the gap is real: `app/Console/` doesn't exist, no class implements `ShouldQueue`, and `routes/console.php` registers only Laravel's stock `inspire` command — `QUEUE_CONNECTION=database` is configured but nothing uses it.

Unlike every other Level 2 gate built this session, this one is not "close review off an existing automated action" — Dot.Press has no natural candidate for that (confirmed: no sharing/publishing concept, no third party whose data an existing process touches). This spec instead builds the automated proposal-generation process *and* its approval gate together, since neither exists yet and the gate has nothing to attach to without it.

## Goal

A new weekly scheduled scan runs `composer audit`/`npm audit`, and — only when advisories are found — creates a pending proposal per package manager naming the exact remediation command. A platform operator reviews it and approves or rejects (rejecting requires a reason). Approving queues a job that actually runs the remediation command and records the outcome; nothing patches dependencies without that approval step.

## Changes

### 1. `is_platform_operator` flag

New migration on `users`: `boolean('is_platform_operator')->default(false)`, excluded from `User::$fillable`, boolean cast added — identical to the ChartSense/Ehail/Emall/Files/Forms precedent. No route or command in this codebase ever grants it; an operator is created by hand.

### 2. `dependency_patch_proposals` table + `DependencyPatchProposal` model

New table: `id`, `manager` (string — `composer` or `npm`), `advisories` (JSON array — each entry: package name, severity, title, advisory/CVE identifier, as parsed from the audit tool's own JSON output), `risk_summary` (text — a derived one-line rollup, e.g. `"3 advisories: 1 critical, 2 moderate"`), `proposed_command` (string — the exact shell command that will run on approval), `status` (string, default `'pending_approval'` — `pending_approval`/`approved`/`rejected`/`applied`/`failed`), `rejected_reason` (nullable text), `reviewed_by` (nullable FK `users.id`, `nullOnDelete`), `reviewed_at` (nullable timestamp), `applied_log` (nullable text — captured stdout/stderr from the remediation run), `applied_at` (nullable timestamp), timestamps. No `proposed_by` column — unlike every prior gate this session, this proposal is system-generated by the scheduled scan, not submitted by a user.

Model `app/Models/DependencyPatchProposal.php`: `$fillable` matching the above (minus timestamps), `reviewer(): BelongsTo` (User via `reviewed_by`), `advisories` cast to `array`.

### 3. `ScanDependencyAdvisories` command

New Artisan command, `app/Console/Commands/ScanDependencyAdvisories.php`, registered in `routes/console.php` via `Schedule::command('dependency:scan')->weekly()`. For each of `composer` and `npm`:

- Runs the audit tool via `Symfony\Component\Process\Process` (`composer audit --format=json`; `npm audit --json`), capturing stdout. If the process errors (binary missing, non-zero exit for reasons other than "advisories found" — `composer audit` exits non-zero when advisories exist, which is expected and not an error condition) or output isn't valid JSON, log a warning and skip that manager — never let one manager's failure abort the other's scan.
- Parses the JSON into a normalized advisory list (package, severity, title, identifier) — the exact field paths differ between `composer audit`'s and `npm audit`'s JSON shapes; the command handles both explicitly, not generically.
- If the parsed list is empty, do nothing for that manager (no proposal when there's nothing to propose).
- If a `pending_approval` proposal already exists for that manager, skip creating a new one — mirrors the "don't duplicate an in-flight request" rule used throughout this session's prior gates (Dot.Ehail's driver applications, Dot.Files' team-deletion requests).
- Otherwise, create a `DependencyPatchProposal` with `manager`, `advisories`, a derived `risk_summary` (count advisories by severity), and `proposed_command` set to a fixed default per manager: `composer update --with-dependencies` for `composer`, `npm audit fix` for `npm` — a single blanket remediation, not a per-package command; scoping to individual packages is out of scope (§ below).

### 4. `ApplyDependencyPatchJob`

New queued job, `app/Jobs/ApplyDependencyPatchJob.php`, implementing `ShouldQueue`. Constructed with a `DependencyPatchProposal`. Runs `proposed_command` via `Process`, with a 300-second timeout, from the application's base path. On success (exit code 0): `status: 'applied'`, `applied_log` set to the captured combined stdout+stderr, `applied_at: now()`. On failure (non-zero exit, or the process times out): `status: 'failed'`, `applied_log` set to whatever output was captured plus the failure reason. **The job always resolves to one of these two terminal states — a proposal is never left `approved` with no recorded outcome**, even if the process itself throws.

### 5. `DependencyPatchController`

New controller, `app/Http/Controllers/Api/DependencyPatchController.php`, and new middleware `app/Http/Middleware/EnsurePlatformOperator.php` (identical shape to every prior platform's — `abort_unless($request->user()?->is_platform_operator, 403)`), registered as an `operator` middleware alias.

- `index(): \Inertia\Response` — Route `GET /operator/dependency-patches`, name `operator.dependency-patches.index`, behind `auth:sanctum` + `verified` + `operator`. Lists `pending` proposals plus a recently-reviewed section (`approved`/`rejected`/`applied`/`failed`), rendering `DependencyPatches/Index` (checked against `resources/js/Pages/Dashboard.vue`'s prop-passing conventions before writing, to match this app's real Inertia/Vue style rather than guessing).
- `approve(DependencyPatchProposal $proposal)` — Route `POST /operator/dependency-patches/{proposal}/approve`. Refuses (flash error, redirect back) unless `status === 'pending_approval'`. Sets `status: 'approved'`, `reviewed_by`, `reviewed_at`, then dispatches `ApplyDependencyPatchJob::dispatch($proposal)`.
- `reject(DependencyPatchProposal $proposal, Request $request)` — Route `POST /operator/dependency-patches/{proposal}/reject`. Same pending-only guard, validates `reason` as `required|string`. Sets `status: 'rejected'`, `rejected_reason`, `reviewed_by`, `reviewed_at`. Never dispatches the job.

## Testing

New test files, matching this app's existing PHPUnit conventions (checked against `tests/Feature/` for the house style before writing):

- `tests/Unit/ScanDependencyAdvisoriesTest.php` — parsing fixture `composer audit`/`npm audit` JSON output (real sample shapes, not invented) creates a `DependencyPatchProposal` per manager with the right `risk_summary`/`proposed_command`; an empty advisory list creates nothing; a manager whose process errors is skipped without aborting the other manager's scan; running the command twice while a proposal is still `pending_approval` does not create a duplicate.
- `tests/Feature/DependencyPatchApprovalTest.php` — an operator can approve a pending proposal (status flips to `approved`, `reviewed_by`/`reviewed_at` set, `ApplyDependencyPatchJob` is dispatched — asserted via `Queue::fake()`, not by letting a real process run); an operator can reject with a reason (status flips to `rejected`, job never dispatched); rejecting without a reason is blocked; a non-operator is refused (403) on the index and both actions; approving/rejecting an already-decided proposal is refused.
- `tests/Unit/ApplyDependencyPatchJobTest.php` — a job whose `proposed_command` is a real trivial command (e.g. `echo ok`, not an actual `composer update`) resolves to `status: 'applied'` with the expected `applied_log`; a job whose command exits non-zero (e.g. `false` or `exit 1`) resolves to `status: 'failed'` with captured output — never letting a real package-manager mutation run inside the test suite.

## Explicitly out of scope

- Per-package remediation commands — `proposed_command` is a single blanket command per manager (`composer update --with-dependencies` / `npm audit fix`), not a targeted fix for each individual advisory.
- Notifying anyone of the scan finding advisories, or of the job's outcome — the operator sees both on the review screen; no email/Slack/webhook is added.
- Any other package manager beyond `composer` and `npm` — this app has exactly these two.
- Rolling back an `applied` patch automatically — if a patch breaks something, recovery is via git/manual intervention, same as today's manual `composer audit` pass.
- A CI/CD pipeline to run this scan on every push — this is a scheduled command only, per the design's explicit choice.
- Registering this change in Dot.Brain's `platforms/dot-press.md` or `platforms/autonomy-signals.json` — a separate, future re-audit pass, not part of building the feature.

## Design decisions confirmed during brainstorming

- **Approval auto-applies the patch** (via a queued job), rather than only recording a decision the operator then executes by hand — matching every other Level 2 gate built this session, where approval is the moment the real effect happens.
- **The scan runs on a weekly schedule**, not only on manual trigger — more genuinely Level 2 (the system prepares the proposal on its own initiative), and gives this platform its first real Level 1 background process, which the audit found was entirely missing.
